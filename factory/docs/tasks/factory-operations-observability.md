# Factory operations and analytics

## Context
- The dashboard shows job stages and host totals, but cannot explain current actions, unused capacity, manager activity or resource ownership. The goal is an operations view that answers more than the GitHub board.
- The inspected main-based checkout is `.worktrees/dashboard-copy` at `a6d7fdfb`. It contains the earlier dashboard copy edits. The main checkout has substantial unrelated, uncommitted factory changes and `save.json`. Preserve all of them. Recheck upstream and overlapping changes before implementation.
- `src/tick.ts` owns job selection but returns selected jobs without rejection reasons. `src/jobs.ts` and `src/container.ts` already identify jobs and label containers. `src/exec.ts` receives output chunks, while `src/ledger.ts` records final usage and job outcomes. `src/dashboard/history.ts` incrementally aggregates the ledger. `src/dashboard/host.ts` measures the whole host, not individual jobs.
- Hermes is the manager. Its factory plugin registers dispatch and routing tools, but the inspected integration has no complete activity lifecycle. Supported runtime hooks must be verified against the pinned Hermes version before choosing an implementation.
- `tmp/factory-operations-mockup.html` and its companion script in the main checkout hold the visual direction with sample data and two tabs. The screenshot review led to compact right-column panels, Server below Manager, functional Analytics charts and worker pagination. These are prototype changes, not runtime integration or verified browser fit. Chromium and its headless shell both failed before rendering, so layout still needs user confirmation.

## Desired design
- Provide two tabs at `/factory/`: Overview and Analytics. Keep the existing game-style fonts and panels, minimal text and no decorative dot separators.
- Overview shows the event log at the top, workers with `Task | Stage | Doing | Progress / elapsed`, unused capacity with actual reasons, funnel counts, a compact next-release summary, Hermes activity and Server resource ownership.
- Analytics shows token counts, estimated cost, worker time and waiting time for 24 hours, 7 days and 30 days. Charts show daily tokens and cost, running versus waiting time by stage, and retry spend. Include model breakdown and measurement coverage without repeating the Overview.
- Capture operational facts automatically at their source. Agents may supply short intent updates when their activity changes, but they do not establish liveness, progress, successful checks or release readiness.
- Extend the existing ledger for durable transitions and keep atomic latest-activity files for live reads. Do not add a database, framework, external monitoring service or another copy of final usage accounting.
- Default no-scroll desktop acceptance sizes are 1440×900 and 1366×768 at normal zoom. When lists cannot fit, provide visible counts and keyboard-operable pagination. Narrow screens and enlarged text must retain access to every item rather than hide content to preserve the desktop layout.

## Invariants and principles
- Do not change scheduling policy, queue limits, CPU allocation, retry behavior, approval gates or deployment rules. The memory admission and exclusive GPU examples in the mockup are hypothetical and must not become claims about the running factory.
- Scheduling decisions and explanations come from the same calculation. Tests must prove selected jobs remain unchanged. A queued task may have several constraints. Record those constraints without inventing an exclusive cause.
- Use job, attempt and producer identities with timestamps and ordering. Old attempts cannot overwrite current activity. Heartbeat, latest activity and last completed step are distinct. An agent report never overrides a confirmed runner event.
- Each producer owns its latest record. Persist meaningful transitions, not every heartbeat or output chunk. Stream structured output and bound record size, history retention and metric sampling through configuration with documented reasons.
- Public output uses an explicit field allowlist. Never expose chat, prompts, raw commands, logs, private paths, unrestricted agent notes or private task titles. Use safe activity categories and approved public issue references. Treat status text as untrusted input.
- Missing, stale and partial measurements remain visible. No fake completion percentages, invented next actions, inferred GPU ownership or zero-filled gaps. Show operational unknowns separately from collector failures.
- Keep observed resource pressure separate from proven scheduling blocks. CPU percentages must have consistent denominators. Do not force host totals to equal process totals when sampling, cache accounting or unattributed usage prevents that.
- Agents cannot write scheduler state through the reporting interface. Reporting failures must be visible, but must not convert successful game work into failed jobs or trigger retries. Preserve lifecycle results and mark observation gaps explicitly.
- Existing historical ledger entries remain readable without fabricated new fields. Waiting and retry measurements begin when their events become available. Final usage remains authoritative, with resumed-session and nested-agent totals counted once.
- Work sequentially in the isolated main-based worktree. No subagents, paid model runs, quality-policy changes, game edits or direct server patches. The owner authorized creating and immediately merging the PR after verification, then verifying the live dashboard. Use the standard updater, including its image rebuilds and service restarts. Preserve running jobs.

## Implementation plan
### Phase 1 — Explain scheduling and preserve operational history
- Add `src/observability.ts` as the owner of typed activity records, safe reporting and atomic latest snapshots. Keep final usage ownership in `src/ledger.ts`. Define validated record fields and producer ownership before wiring writers.
- Extend `src/ledger.ts` and its consumers with scheduling, waiting and activity transitions. Audit `src/waste.ts`, `src/dashboard/history.ts` and `lineTime` so new event kinds do not corrupt existing reports. Record changed decisions only, with coverage start and collection gaps.
- In `src/tick.ts`, have one decision function produce both chosen jobs and explanations for excluded work and unused queues. Include queue saturation, same-issue activity, daily cap, stuck or needs-info labels, release prerequisites, priority and no eligible work.
- Report global pause, disk-space gating, tick start/end and tick errors from `src/cli.ts` and `src/tick.ts`. Derive next timer activity from actual timer configuration rather than a hardcoded countdown. Keep pause reasons private unless represented by an approved public category.
- Link retries and resumed attempts through lifecycle records in `src/job.ts`, `src/jobs.ts` and `src/tick.ts`. Capture issue state transitions for waiting durations and funnel counts, excluding private work from public references.

### Phase 2 — Report worker activity and progress
- Extend `src/exec.ts` and `src/container.ts` with incremental structured-event handling. Record operation start/end and runner liveness without copying raw arguments or tool output into public records. Parse agent output across chunk boundaries and preserve current execution results.
- Instrument known factory steps in `src/stages/checks.ts`, `src/deploy.ts` and `src/lock.ts`: dependency installation, tests, typecheck, playtest, build, publishing and lock waiting. Report test counts only from supported structured runner output, not guessed progress.
- Add a narrowly scoped reporting command through `factory/docker/factory-agent` and its image configuration. Agents can report an activity category, task context and intent at phase changes. Job identity is supplied by the runner, not trusted from the agent. Private free text is not copied to public snapshots.
- Update the shared agent instructions and affected prompts to use the reporting command when purpose changes. Do not require repetitive status narration or extra model turns. Test with recorded structured-output fixtures and disposable processes, not paid agents.

### Phase 3 — Observe Hermes, resources and release gates
- Verify native lifecycle and tool hooks in the pinned Hermes source/documentation. Add activity reporting in `hermes/plugin/` for task receipt, safe operation categories, waits and completion. Use an explicit manager reporting tool for intent that hooks cannot capture. Never patch installed Hermes files. Stop for a scope decision if a runtime upgrade is required.
- Associate manager actions with incidents and public issues where safe. Show idle, active, waiting, stale and unknown distinctly. Instrument the incident watch so detection is not confused with Hermes actually starting an investigation.
- Extend `src/dashboard/host.ts` to sample job containers/process groups using existing labels. Report CPU, memory and disk activity by job and safe service name, resource pressure within configured CPU pools, and unassigned usage. Add GPU process attribution only where the host driver supplies reliable evidence.
- Extract shared release-readiness queries from `src/tick.ts` and release stages where necessary. `src/dashboard/snapshot.ts` uses those same queries to show included changes, outstanding work and the next unmet gate. Preserve distinction between feature approval and permission to ship a candidate.
- Put sampling, freshness and retention settings in the existing environment configuration and examples. Keep the collector read-only and avoid giving the public web process broad host-control access.

### Phase 4 — Build Overview and Analytics from recorded facts
- `src/dashboard/snapshot.ts` owns the public projection of current operations. `src/dashboard/history.ts` owns bounded aggregation of recorded transitions and usage. Neither reconstructs scheduler policy or analyzes private chat.
- Define metric semantics in code and tests: worker time sums job durations, waiting time measures observed non-running intervals, retries include linked repeat attempts, token totals include reported cache categories, and cost remains estimated. Reconcile cumulative usage before aggregation. Do not add historical guesses.
- Replace the prototype markup in `dashboard/index.html`, `dashboard/dashboard.js` and `dashboard/dashboard.css` with the agreed two-tab interface. Use Server throughout. Preserve the compact release summary, current funnel, event log and exact worker columns. Keep the right-column summaries content-sized and place Server below Manager instead of squeezing it into a fixed bottom strip.
- Add real tab behavior, accessible selection state and keyboard navigation. Analytics range changes update counters and charts together. Keep details available without copying the same status into multiple panels.
- Make every growing collection bounded in the visible layout: workers, unused-capacity reasons, events, blockers, process rows, model rows and issue rows. Show total and visible ranges, support pagination, and preserve current page and focus during live updates. Clamp pages when their contents shrink.
- Reserve widths for numeric fields and compact their display while retaining exact values in an accessible detail view. Limit long titles, activities, errors and release summaries without losing full text or issue identity. Do not silently clip panels or shrink text to force fit.
- Charts use a bounded number of time buckets for each range, readable units and distinct missing-data states. Cover empty, one-point, zero, partial, stale and extreme-value series. Expose values through accessible text, not hover alone. Do not imply two metrics share a scale when they do not.

### Phase 5 — Verify and prepare delivery
- Update dashboard usage and measurement documentation with actual reporting fields, privacy boundaries, supported host readings and overflow behavior. Do not rewrite unrelated factory guidance.
- Run focused tests after each phase, then factory typecheck and the unchanged repository quality gate. Run affected Hermes/plugin and infra tests where those files change. Install dependencies only within the worktree.
- Run browser checks and the final manual try against disposable local records, including replayed live updates. Browser launch failure is a verification blocker, not a passing layout check. Have the user confirm the rendered desktop layout.
- Commit only this task's files and submit a pull request against `main`. Leave merge control to the user. Document the required image/config rollout separately because agent reporting and Hermes integration may need more than the ordinary code updater.
- After explicit deployment approval, use native release/update paths and restart only the required services. Verify new observations arrive without stopping existing jobs, inspect public privacy and health, and confirm `/`, `/dev/` and existing build routes remain intact.
